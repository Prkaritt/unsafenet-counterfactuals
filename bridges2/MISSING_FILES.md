## Discrepancy found while checking — RESOLVED 2026-11-04

`STATUS.md` reported the T4 generation as **40 steps** where `configs/experiment.json`
specifies **50**. These never conflicted. `CogVideoXVideoToVideoPipeline.get_timesteps()`
truncates the schedule by `strength`, running
`min(int(num_inference_steps * strength), num_inference_steps)` steps. At the configured
50 steps and strength 0.8 that is exactly 40. Verified against the diffusers 0.36.0 source
installed in the environment, and confirmed by the Bridges-2 run of 2026-11-04, whose
progress bar also shows 40 steps for a requested 50.

What was genuinely wrong was the derived timing. `run_baseline.py` divided elapsed
generation time by the *requested* step count, so every `s_per_step` it has ever written is
understated. The T4 line

> Generation (40 steps, strength 0.8) — 820.5 s (13.7 min), 18.78 s/step

is internally inconsistent for that reason, and 18.78 s/step should not be used as a
comparison figure. Total wall time for the generation call, 820.5 s, remains usable.

Fixed in `scripts/run_baseline.py`: `denoising_steps()` computes the executed count, the
manifest now records `num_inference_steps` and `denoising_steps_executed` separately, and
the timing field is `s_per_denoising_step`. Covered by `tests/test_run_baseline_settings.py`.

Note that `generation_s` still measures the whole pipeline call, which includes VAE encode,
text encode and VAE decode as well as the denoising loop, so it exceeds
`denoising_steps_executed` multiplied by the progress bar's per-step time. The 2026-11-04
run shows this clearly: 93.0 s elapsed against 40 steps at about 1.55 s/step, so roughly
31 s is fixed overhead outside the loop. The manifest note records this.
